## 2. 先说结论
- **今天最值得看什么：** [AgentSSL: Can MLE Agents Leverage Unlabeled Data?](http://arxiv.org/abs/2611.17323v1)（arXiv 2611.17323，Ethan Lin / Akanksha Sarkar 等，Cornell University + HHMI，**NeurIPS 2026**）——**它把 agent 搜索的瓶颈从「能不能造出来」精确地挪到了「能不能挑出来」，并且用两张表把这个落差量化到了 47 个百分点**。
- **为什么值得看：** 三条理由，每条都有今天的实测支撑。
  - **其一，它的正面结论是可用的：「agent 写出的 SSL 程序在 12 个设定里有 8 个打赢了最强的人工基线」，最大优势 RETINO 40-shot **+21.81 个百分点**（73.47 vs 51.60）。** 但这个 +21.81 有个必须写在同一行上的前提——**它是「用测试集做 oracle 挑选」之后的结果**。
  - **其二，它的负面结论才是今天最值钱的一半：**「**用 agent 自己的反馈指标去挑程序**，选择损失最高达 **−47.29 个百分点**」（RETINO 80-shot，noisy-validation 反馈）。**这意味着「agent 搜出一堆候选、再用 agent 自己的评分挑一个」这个我们天天在用的流程，在无标签场景下会系统性选错最多 47 个点。**
  - **其三，它给出了第三层解法：**当无监督指标失效时，**把标签预算对半分给「训练」和「主动选择」反而更好**（RETINO 上 +25.59 / +26.07 / +26.07，KITTI 上 CODA +14.63），但**在无监督指标本来就管用的数据集上会倒退**（CODA 在 CLEVR 20-shot 是 **−29.09**）。**即「花标签去挑」本身也有适用边界。**
- **它属于什么价值类型：** 即时价值。
- **今天该做什么：** 今天就把**「选择」从「生成」里单独拆出来当成一个评测对象**——我们自己的多 prompt / 多方案 A/B，现在默认「agent 自己评自己的分」就是选择机制，**这条要立刻改成「选择器的排序与真实结果的秩相关」作为一个独立指标**。
- **最大不确定性：** **本文最重要的资产今天打不开**——HuggingFace 全站实测 4 次请求全部超时，**ProgramSelectBench（16,977 个 program、35 个任务、>10,000 GPU 小时）今日完全无法核验**；仓库 `akanksha-sarkar/AgentSSL` **无 LICENSE**、★0、forks=0、**pushed 停在 2026-10-04**（比论文早 5 周）；且论文自陈在真实生态学任务（WildFin / BuckTales）上 **AgentSL 与 AgentSSL 打平**。

- **一句话本质：** 不再问「agent 能不能造出好程序」，而是问「**agent 造出一堆程序之后，谁来挑，以及挑错的代价有多大**」——并把这两个问题分开测量。
- **底层问题：** MLE agent 已经被证明能自动化「写代码」这件事（论文引 MLE-Bench 的 75 个 Kaggle 竞赛：**一年之内最优 agent 的平均百分位排名从 45.2% 升到 83.1%**）。但**几乎所有既有 agentic benchmark 都假设有充足标注**（MLE-Bench 的任务动辄数千到数百万训练样本），**于是 agent 被优化成了「在标注充裕的假设下搜索」**。现实中相反：科学发现、医学诊断、环境监测这些领域**标注稀缺而无标注数据充裕**。
- **挑战了什么旧假设：** 它挑战了「**搜索反馈信号越好，搜出来的东西就越好**」这一默认假设。证据是反过来的：**论文实测在反馈信号与测试精度「弱相关甚至负相关」的条件下，agent 仍然能搜出超过人工基线的程序**（8/12 设定），但**一旦换成「用这个反馈信号去挑程序」，同一批程序的选择损失最高达 −47.29 个百分点**。**即「信号够不够好」和「信号够不够用来做选择」是两个不同的问题。**
- **新假设：** **「随着 agent 让候选程序变得廉价可生成，瓶颈会从『造程序』转移到『挑程序』。」** 这句话是论文自己的结论（原文：'as agents make candidate programs cheap to generate, the bottleneck in AgentSSL shifts from building programs to choosing among them'）。它还有一个更狠的推论——**「更强的 agent 不会缩小这个差距，反而可能放大它」**：论文原文明确写 'Stronger agents will not close this gap and may widen it: the more programs an agent generates, the larger the gap can grow between the best program and the one chosen without labels.'
- **核心机制（三层，今天逐层核对过）：** **① 程序发现**：agent 在隔离的 Apptainer 环境里执行候选程序，把执行日志、错误、fitness 分数返回给 agent 做下一轮搜索；**搜索预算是按基线的计算成本对齐的**（DTD/RESISC45/KITTI 各 8 小时 RTX 6000 Ada，SUN397/RETINO/CLEVR 各 15 小时 H100 或 RTX 6000 Blackwell Max-Q）；**② 程序选择**：从候选池里用无监督指标或主动选择挑出**一个**；**③ 主动选择**：当无监督指标失效时，把标签预算分一部分给选择而非全部给训练。论文还诚实交代了一个机制缺陷：**表征类指标无法区分「复用同一冻结表征、下游 SSL 流程不同」的程序**。
- **工程可验证性：** 今日实测 `github.com/akanksha-sarkar/AgentSSL` **5,364 blobs / 2,866 目录 / 665,761,812 B ≈ 666 MB**；**实读了 `eval/evaluate_program.py`（7,989 B）**——是真代码：把四个 BLAS 线程数环境变量钉为 1（注释逐字 'avoid OpenBLAS/MKL threading segfaults on some clusters'）、`sys.path.insert(0, '/work')` 绑容器挂载点、`faulthandler.enable()`、数据集名未知时**显式 `raise KeyError` 并列出已知数据集**；`eval/nets/vit_petl/` 带 13 个 py（adapter/attention/block/fact/lora/mlp/patch_embed/repadapter/ssf/vpt…），`metrics/metrics.py`（6,899 B）齐全；顶层 8 个数据集目录（archive 2,731 / dtd 929 / retino 268 / kitti 242 / inat 189 / clevr_count 180 / sun397 72 / resisc45 61）逐设定带 `description.md`、`annotations/`、特征缓存。**但 666 MB 的仓库、无 LICENSE、pushed 停在 10-04，README 自己写着 'Data Storage (Not sure how this looks right now?)'。**
- **趋势关联：** 直接落在 **AI Agent** 与 **LLM 评测** 两条主线上；它和 2026-11-11 那天的 WorkflowArena（测「agent 能不能自己组织工作」）构成同一条线索的两端：**WorkflowArena 测组织能力，AgentSSL 测选择能力**——**而组织能力变强会让候选变多，选择问题只会更严重。**
- **长尾价值：** 即使我们永远不做 SSL，**「选择器本身必须被当成一个独立评测对象」这个判断长期可复用**——它可以迁移到我们所有的「生成 N 个候选再挑一个」的场景：prompt 变体、检索重排、工具选路、模型路由。
- **启发：** **「候选越多，选择器越可能是系统的真正瓶颈。」** 今天实测的 47.29 个点差距，就是「候选变多」的代价。**我们每增加一个 agent 方案、一次 A/B 迭代、多一个模型路由分支，都在把系统推向「搜索不是瓶颈、选择才是」的那个状态。**
- **行动建议：** 今天给我们的多方案 A/B 流程**加一个指标**：「选择器的排序与真实结果的秩相关（rank correlation）」——**这个数今天就能算，成本为零**。

## 7. 启发

### 系统设计启发
- **今天最值钱的一条：候选越多，选择器越可能是系统的真正瓶颈。** AgentSSL 实测：同一批程序，**用 agent 自己的反馈指标挑，最差比 oracle 挑选低 47.29 个百分点**。**→ 我们的直觉是「多生成几个方案总比一个强」，今天这批数据提醒我们：如果挑选用的是同一套自评信号，那多生成候选可能只是把噪声放大。**
- **「用测试集挑」和「不用测试集挑」是两个不同的问题，但论文把它们放在同一张表里比较。** Table 1 的 +21.81（oracle）和 Table 2 的 −47.29（实用选择）**描述的是同一批程序**。**→ 这提醒我们：报一个 agent 论文的漂亮数字之前，先问「这个数字是选出来的还是搜出来的」。**
- **「花标签去挑」也有适用边界。** 实测：标签对半分在 RETINO 上 +26.07，但在 CLEVR 20-shot 上 CODA 是 **−29.09**。**→ 没有普适最优策略，先测哪类场景哪种有效。**

### Agent 工程启发
- **「选择」必须从「生成」里拆出来当独立环节。** 论文结论逐字：瓶颈从 building programs 转向 choosing among them；**更强的 agent 不会关闭这个差距，反而可能放大它**。**→ 我们加 agent 方案时，第一问不该是「能不能多生成」，而是「用什么选」。**
- **表征类指标会看不见「下游流程不同」的程序。** 论文实测：agent 搜出的高分程序常复用同一冻结表征、只换下游 SSL 流程，**此时表征指标无法区分它们，尽管预测性能差距可能很大**。**→ 这条直接命中我们：凡是用 embedding 相似度 / 表示质量当选择信号的场合，都要警惕同一类盲区。**
- **写 memory 之前要问「下一个任务用不用得上」。** 今日 CoReMem 实测：**「无脑塞全量历史」只有 +2%~+7% resolve 且 token 反涨 +5%~+21%（纯亏）**；而带溯源门控的 CoReMem 在 Qwen3.8-27B 上 resolve 21.0%→25.7%、token −11%。**→ 我们的 agent 记忆模块，今天就该算一遍「塞全量历史 vs 只留锚点」的 token 与成功率账。**
- **「错误信息在隐藏状态里，不在置信度里」这条要记下来。** 今日 DiVR 实测：隐藏状态探针区分错/对格子的 **AUROC 0.838**，而 token 置信度只有 **0.685**。**→ 我们 agent 的 self-check 现在主要用置信度/自评，DiVR 说明这可能并不可靠。**

### 评测方法启发
- **先问「指标本身会不会被混淆」，再下结论——今天第三次出现这条。** Unbundling 的核心前提正是「已发布模型在数据、架构、算力上全都不同，比较它们无法隔离任一选择」；**它的解法是「只让一项不同，其余全部从随机初始化自己跑一遍」。**
- **停止规则的「误停率」可能比准确率更值得抄进评测表。** 今日 CRAM 实测停止规则对照表：**CRAM（能量阈值）Wrong halts 0.00%**，而 HRM 0.62%、TRM 2.37%、EqR 1.61%、TRMP 0.05%、EBR 0.21%。**→ 我们的 agent 现在靠 token 上限和超时硬停，从没量过「停早了」的误停率。这张表值得抄。**
- **「不做事后拦截、让合规被学进策略」是一个值得尝试的论证方式。** 今日 2611.17329 实测：违规率从无约束 RL 的 96–98% 降到 **4.8%**，且**推理时无任何强制机制**。**→ 我们 agent 的安全约束现在多是「违规扣分」，可以试一次「把约束学进策略/流程本身」。**
- **「结构稳定性是预测稳定性的上游」这个排序可以借用。** 今日 2611.17308 实测：我们做模型更新时通常只看预测漂移，不看结构漂移；**而结构先变、预测才变**——**先量结构，是一个便宜的早期预警。**
