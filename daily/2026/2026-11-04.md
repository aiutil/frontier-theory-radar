## 4. 今日深挖论文

- **一句话本质：** GUI web agent 的评测一直卡在同一个矛盾上——**真实网站会变、会拦登录、会被反爬，但只有真实网站才测得出真本事**；WebHarbor 的做法是**用 coding agent 把 153 个真实网站镜像成本地 Docker**，让「环境」从「会漂移的外部依赖」变成「可复现的、可版本化的、可训练的数据资产」。
- **底层问题：** 不是「模型不够强」，而是**评测环境本身不可靠**。live web 有三个具体缺陷：内容漂移（同一任务两次跑分不同）、访问限制（登录墙、验证码）、覆盖不足（尤其是**认证后的多步流程**——这恰是真实业务里最常见的那类）。而现有的合成环境（冻结成玩具站点）又缺功能深度和视觉保真度，训出来的 agent 一到真站点就崩。
- **挑战的假设：** 它挑战的是「**评测环境必须是死的，训练环境必须是活的**」这个默认分工。WebHarbor 把两者合并成同一批环境——既能评测也能做 RL 训练，而且**环境会随 agent 能力一起演进**（这是它的 README 里明确写的设计目标：Environments evolve with agent capability）。
- **新方法：** 三层。**构建层**：用 Claude Code / CodeX 这类 coding agent 把真实站点复刻成本地 Docker，每个站点一个端口（40000+i），控制面在 :8101 带 token 保护、可把任一站点重置回种子状态。**质量层**：**人机协同 + 人工审计**——环境随新任务扩展功能范围，coding agent 负责实现改动，人类贡献者负责审计视觉保真度、功能正确性与任务有效性（这是保证 153 个环境不沦为空壳的关键，也是最容易被复制者忽略的脏活）。**评测层**：153 个环境、3,518 个任务（含认证后流程），另有 306 个 verified 测试任务。
- **新能力：** ① 在 RL 训练里使用真实站点的功能深度与视觉保真度，而不受网络噪声影响；② 一个 4B 级 GUI agent 能靠这套环境训到 **WebVoyager + Online-Mind2Web 平均 75.8**，README 声称是 4B 规模最好的开源 GUI web agent；③ **代理环境与真实站点的分数可互换用于排序**（6/6 成对排名保持、Spearman 1.00、Pearson 0.80）。
- **工程可验证性（今日已实测的部分）：** 仓库存在且结构完整（Dockerfile、requirements.lock、control_server.py、harbor/、sites/、AGENTS.md、CONTRIBUTING.md）；`sites/` 目录**实测 153 个子目录**，与论文一致；数据集与模型权重在 HF 镜像上实测存在且刚更新。**今日未能验证的部分：** hub.docker.com 全程超时 → 镜像能否真正 build、20 GB 体积、tag 数均未核实；仓库**无 LICENSE**；论文无 HTML 全文，所有实验数字为作者自述。
- **趋势关联：** 直接强化 `coding-agent` 与 `llm-evaluation` 两条趋势线。更值得注意的是它**贡献的是环境而不是模型**——在当前 agent 生态里，「模型」天天有、「可复现的评测环境」稀缺。
- **长尾价值：** 即使我们不用它做训练，它也值得存为「**评测环境工程化**」的方法论样本：把外部世界固化成可版本化资产，是一切可复现研究的前提。
- **启发：** **我们自己的评测环境有多少是「活」的、多少是「死」的？** 如果我们的 agent 评测跑在真实 SaaS 上，那么我们现在就有和 WebHarbor 要解决的同一个问题，只是还没有意识到。可以先把**最常用的 3–5 个内部系统**做同样的镜像固化。
- **行动建议：** 今天不下载完整 20 GB 镜像；先只拉 2–3 个站点镜像验证我们的 agent 在「稳定环境 vs 真实环境」下的分数差异，把「环境漂移对分数的影响」量化出来，这本身就是今天最有价值的一个内部结论。

- **为什么现在不火也值得保存：** 今日第五价值，**技术密度最高但今天完全无法验证的一篇——它的数学很扎实，可它连一行代码都没放**。★ 核心问题（论文摘要口径）：group-based RLVR 只从采样结果有分歧的 prompt 里学习，**全对（all-pass）和全错（all-fail）的组相对优势为零，白烧生成预算还不推进策略**。自适应调度器的做法是把 rollout 引向有信息量的 prompt，但这些调度器依赖**每 prompt 的 pass-rate 追踪器**，而 pass-rate 把**两个演化速度完全不同的量纠缠在一起**：(1) 策略在各推理技能上的**能力在漂移**（快），(2) 每个 prompt 的**内在难度**（慢）。用单一指数平均或 Beta 计数器同时跟踪两者时，**短记忆会打乱 prompt 的相对排序，长记忆则报告陈旧的通过率**。★ 方法（FADE = Factored Ability–Difficulty Estimation）：把每个 prompt 的成功 logit 表示为**白化后的 K 维技能载荷与快速漂移的策略能力向量的内积，减去一个缓慢收缩的标量 item 截距**——即用**双线性状态空间滤波**把能力与难度在两个时间尺度上分离。用 **Pólya–Gamma 增广**，每个 minibatch 的二元 rollout 结果通过 **rank-K Woodbury 步**闭式更新 K 维能力后验，**能力变化会立刻传导到所有共享这些技能的未观测 prompt，同时保持 item 截距稳定**；再由后验均值与方差导出**抽到非退化 rollout 组的概率的闭式 utility**。实测口径：**5 个推理 benchmark、2 个基座模型、4 种调度范式，在相同 rollout 预算下，FADE 持续提升下游准确率与校准，每步额外开销 < 0.6 ms**。★ 独立执行（论文全文核对，确认了它到底有多完整）：arXiv HTML 全文可读，结构包含 §4 理论分析（含 Minimax 时间尺度分离证明）、附录 A 数学推导与证明（**A.1 共轭 Pólya–Gamma 滤波步、A.2 零样本方差收缩、A.3 Minimax 时间尺度分离、A.4 方差感知组 utility 的推导**）、附录 B 实现与集成细节（**B.1 技能基构造与数值稳定性、B.2 与宿主 RLVR 调度器的集成**）、附录 C 附加实验（**C.1 与 VIP rollout 分配器的集成与多种子稳定性、C.2 跨模型规模 1B→7B 扩展、C.3 对技能维度 K、保留系数、编码器选择的敏感性**）、附录 D 扩展讨论（**为什么双线性分解优于图聚类与消息传递、何时 FADE 退化为更简单的估计器**）。→ **这份附录结构本身就是这方法被认真做过的证据**，也说明它不是拍脑袋的滤波器。★ 证据边界（今天的实际情况，必须诚实）：(1) **全文检索 code is available / code will be / available at 零命中，GitHub 上按 FADE ability difficulty RLVR 检索 total_count=0**；作者账户 duncun（public_repos=0）、ingridsolberg（public_repos=1，均非本仓库）**都没有对应的公开实现** → **今日无法执行、无法复现、无法核对任何一个数字**；(2) 论文**没有给出开源计划声明**（连 will release 这类措辞都没有），**代码状态标记为待核验/暂无**；(3) 5 benchmark / 2 模型 / 4 调度器的实验规模在论文里属中规中矩，**且全部是论文自述**；(4) 作者名单（Tomas Duncun、Jonah Ellison、Mateo Ruiz、Hanae Fujita、Ingrid Solberg）在 GitHub 上**均无关联公开仓库**，无法交叉验证。★ 为什么给长尾价值而不是忽略：它诊断的问题（**能力与难度的时间尺度纠缠导致调度器排序错乱**）是 RLVR 工程里的真问题，附录 B.2 与宿主 RLVR 调度器的集成说明它被设计成可插拔组件，**一旦开源就是可直接接入的**；而且其中的多时间尺度分离思路本身可以现在就用在我们的 RL 数据采样上。→ **存进长尾库，触发条件：出现公开实现 / 被其他 RLVR 调度论文引用 / 我们的调度器出现 pass-rate 排序错乱的实证。**

## 7. 启发

### 系统设计启发
- **把「环境」当作一等的可版本化资产，而不是每次运行的副产品。** WebHarbor 最值得抄的不是 web agent，是它**用 coding agent 生成环境**这件事本身——这是「用 agent 造评测环境」的自我强化闭环。我们自己完全可以把高频接入的 3–5 个内部系统做成镜像化的稳定环境，让回归测试摆脱上游抖动。
- **注意 WebHarbor 给出的那条量化校准：代理环境分数比真实站点高 4.4–18.8 分，但排序完全一致（Spearman 1.00）。** 这是「代理指标可用」的**精确边界条件**：**排序可以用，绝对值不能用**。我们的很多内部代理指标（自动打分、模拟用户、LLM 评审）大概也处在这个位置，值得同样去量一条「代理 vs 真实」的校准曲线。

### Agent 工程启发
- **人工审计是这个体系里最不可省略的一环。** WebHarbor 的 153 个环境是「coding agent 实现改动 + 人类贡献者审计视觉保真度与任务有效性」的产物。**纯靠 agent 自动生成环境、无人审计，规模一大就会退化成看起来像但其实是空壳的站点**——这条对我们自建 agent 评测环境是直接可用的教训。
- **「环境的演进随 agent 能力演进」是一个值得抄的设计。** 静态环境集很快就会不够用；让环境跟着我们 agent 的失败模式一起长，比每次重做一套环境便宜。

### 研发流程启发
- **RLVR 论文给了一条反直觉但极实用的数据配比原则（今日第二篇 RLVR）：** outcome-only 的 RLVR 其实在**隐式地为正确的推理策略记账**，所以「混入能强化推理过程的任务」比「只堆更难的题」更有效——而且那些辅助任务**离最终评测分布更远也没关系**。这条直接可用于我们的 RL 数据配比。
- **方法论诊断比分数更有价值。** 那篇 RLVR 论文真正的贡献不是「RLVR 有用」，而是「**RLVR 训对了策略，但策略在 OOD 会退化成暴力枚举**」这个可测量的失败模式。**没有这个诊断，我们会一直以为是自己 prompt 写得不好。**

### 评测方法启发
- **D&A 的「先描述、后评估」是一个可以直接搬走的通用模式。** 先让模型**在不知道任务目标的前提下**客观描述发生了什么，再用一份**显式的绝对判据（rubric）**去评进度——**把判定锚定在外部全局标准上，而不是视频/轨迹自身的时间轴上**，从而消除确认偏置（失败执行里幻觉出进度）。这个模式不限于机器人视频：**审代码、评作业、看 agent 轨迹、判断一段对话有没有解决问题，全都可以用「描述 → 对照显式判据评分」两步走。**
- **我们评测里的「绝对分 vs 相对序」要分开记录。** WebHarbor 用 6/6 排名一致 + 1.00 Spearman 证明了「合成环境能替代真实环境做排序」这件事——**但同时用 4.4–18.8 分的偏移量提醒你不能拿绝对分汇报**。我们的任何离线评测都应该配一条这样的校准说明。
