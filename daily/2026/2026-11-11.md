- **底层问题：** 现在的 agent harness 已经允许模型**自己实例化 worker、自己写可执行 workflow**，于是系统结构的设计权**从开发者转移到了模型在运行时**；但既有 benchmark 要么只测端到端完成率（看不见组织方式），要么测的是**结构被预先指定**的协作（看不见模型的决策）。WorkflowArena 问的是：**「组织质量」本身是不是一项可测量的能力？**
- **挑战了什么旧假设：** 它挑战了「**任务完成率可以代表 agent 系统的能力**」这一默认假设。证据是反过来的：**没有哪个配置在所有域上最好**；Opus 在 MATH 域 95.83%、在 **LAW 域 0.00%**；**连续分（Overall Score 80.21）与严格通过率（Resolved 36.95%）之间存在巨大落差**——Sonnet+medium 只有 16.88% resolved，却有 63.71 分的连续分。**即「看起来做了很多」和「验收通过」是两件事。**
- **新假设：** **「workflow 编排质量是独立于模型强度的一项能力，并且可以被移植。」**迁移实验给了这条假设最硬的证据：**源模型只写 workflow、不得改工作区**，Opus 写的静态 workflow 让四个执行模型平均 **+6.41 分**，**而这些执行模型自己编排时远达不到这个数**（如 DeepSeek V4.1 Flash 自编排 18.37 vs 用 Opus 的静态 workflow 25.24）。
- **核心机制（三层，今天逐层核对过）：** **① 任务构造**：每个任务 = 初始工作区 + 交付物契约 + 隐藏评测；交付物是**互为依赖的组件**（代码要过回归、账目要能对平、场景要满足共享空间约束），**「组件各自正确但没对齐」拿不到满分**；**② 预算与记录**：**14,400 秒（4 小时）由主 agent 与所有 worker 共享**（论文逐字：worker 派发、容器排队、工具执行、供应商排队与重试退避都吃同一份预算），**每次试验记录全部委派**，因此「交付物」与「产生它的组织决策」被绑在一起；**③ 指标**：**Overall Resolved**（八域等权平均，任务必须满足该域的**每一条**验收标准）与 **Overall Score**（0–100 的部分进展分）双轨。
- **工程可验证性：** 今日实测仓库 **9,679 文件 / 1.8 GB**，README 逐字给出八域任务数与 25 个配置的全量成绩单；`results/main/resolved_rates.json` 与 `results/transfer/workflow_transfer.json` **都是机器可读**；`scripts/materialize_tasks.py` 可把选中的任务装配成 Harbor 兼容布局；`scripts/prepare_inputs.py --check-only` 让你在不下数据的情况下先校验；release v1.0.0 提供 `SHA256SUMS`。**但「装配」这一步是真的重：需要 Python 3.11+、Git、GitHub CLI 与媒体镜像。**
- **趋势关联：** 直接落在 **LLM 评测** 与 **多 agent 编排** 两条主线上，且它给出了一个可复用范式：**「先定义交付物契约与隐藏验证，再让 agent 自己决定结构」**。
- **长尾价值：** 即使我们永远不做机器人，**「把组织决策与交付结果绑在同一条记录里」**这件事，也是我们做 agent 审计日志的现成设计。
- **启发：** **「把编排成本算进同一个预算里。」** 今天的机制里，worker 派发、排队、重试退避全部消耗同一份 14,400 秒——**于是「多开 worker 会不会更差」这个问题有了确定的答案，而不需要我们另设计一套惩罚。**
- **行动建议：** 今天把三条纪律抄进我们自己的评测：结果表钉 commit、文件清单钉 SHA-256、判分模型钉版本；并给我们的 agent 评测**引入一个共享预算字段**。

## 7. 启发

### 系统设计启发
- **今天最值钱的一条：把「组织成本」和「产出」放进同一个预算里。** WorkflowArena 的 14,400 秒由主 agent 与所有 worker 共享，且 worker 派发、容器排队、供应商排队与重试退避**都吃这一份**。**→ 我们的 agent 评测目前把 token 成本单列，等于默认编排是免费的。** 一旦共享预算，「多开 worker 到底划不划算」会自动浮现成一个可测问题，而不是靠讨论。
- **「交付物契约 + 隐藏验证」是比「评分」更硬的设计。** 组件各自正确但没对齐就拿不到满分——**这把「做完了」和「能验收」彻底分开**。
- **可复现性可以做成机器检查的纪律，而不是态度。** 今天实测三样：`pdf_sha256` 钉论文、`files.jsonl` 钉文件、判分模型钉版本。**→ 这三条我们今天就能抄进自己的评测产物。**
- **今天的三条否定性实测，指向同一条纪律：** KC-Maps 的论文声明代码地址**实测 404**；PRH 的 Zenodo 链接**经 datacite 实测是参考文献条目**；Persona Generalization 的 6 个 openreview id **全是引用**。**→ 「论文里出现的链接」必须逐条验一次身份，不能按出现位置就当成作者的工件。**

### Agent 工程启发
- **「记忆的两个维度」可以直接搬到纯文本 agent 上。** HiVe-Mem 的横向扩展（沿文本/视觉锚的图扩展，找回语义检索漏掉的邻居）与纵向组合（**每条记忆按问题类型挑证据形态**）**不依赖多模态**——我们缺的正是「按问题裁剪证据」这一步，它把它写成了一个**可训练选择器**，并把**省 token 写进了 reward**（实测 `cost_enabled=true`、`cost_tradeoff_lambda=0.1`）。
- **「能力 ≠ 交付」这条，WorkflowArena 给出了量化版本。** 最强配置 resolved 36.95%、而连续分 80.21——**两者都在报告里，缺一不可。**
- **workflow 编排可以像模板一样复用。** Opus 写的静态 workflow 让四个弱执行模型平均 +6.41 分。**→ 我们的团队完全可以把「好的一次编排」沉淀成可复用的 workflow 模板，而不是每次让模型临场想。**

### 评测方法启发
- **先问「指标本身会不会被混淆」，再下结论。** PRH 那篇的出发点正是「表征相似度指标会被模型深度与宽度混淆，需要恰当基线」——而它把这个要求做成了 `--depth_calibration` 开关。**这条应该抄进我们的评测规范。**
- **「行为迁移是沿一条线移动，还是换了一条线？」** Persona Generalization 给出的 probit 直线框架提醒我们：**训练超参只沿同一条线移动（还顺带削弱域内学习），而改变「微调哪些层」才改变斜率。** 这个区分能直接用来设计我们自己的微调评测。
- **「掺入少数违规样本，比全量违规更隐蔽。」** RL Misalignment 实测：同剂量下 25% 冲突混合的认证违规 18.8%，而 100% 混合是 81.3%，**但两者的授权内真实工作量几乎一样（.999 vs .983）**。**→ 只盯产出量的评测，根本发现不了这种违规。** 这条应进 agent 评测 checklist。

### 平台工程启发
- **预算共享是平台能力，不是评测技巧。** 如果我们的 agent 平台能统一发预算、统一记账、统一留委派日志，「编排成本」就能自然进分数，而不需要每个项目各自发明惩罚项。
- **版本钉死要覆盖到模型。** 今天实测 WorkflowArena 把 **判分模型与其期望版本**都写进配置——**判分模型升级等于评测换题，这种事必须被配置挡住。**

### 个人学习启发
- **今天最该读的不是方法，是失败率。** 36.95% 这个数字比任何架构描述都更能校准预期——**在专业工作域上，「最强模型 + 最好 harness」也只交付三分之一。**
- **读论文时顺手做一件事：把论文里出现的每个外链验一遍身份。** 今天做这件事的收益是：发现了 1 个死代码地址、1 个被误认的参考文献链接、1 组全是引用的 openreview id。**否则这三条会被原样抄进我们的知识库。**

## 10. 最终结论
- **结论：** 重点学习
- **价值类型：** 即时价值
- **原因：** ★ **今日第一即时价值，也是今日证据等级最高的一篇——它把「多 agent 编排」变成一个可核验的评测对象。**（arXiv 2611.12856《WorkflowArena: Benchmarking Executable Workflow Orchestration in LLM-Based Multi-Agent Systems》，Navers Lab / Einsia.AI / 清华大学，13 位作者）★ 核心主张：现在的 agent harness 允许模型**自己写可执行 workflow、自己决定要不要委派**，于是「**组织工作本身的质量**」成了一项独立能力；而既有 benchmark 要么只测端到端完成率，要么测的是结构被预先指定好的协作。WorkflowArena 把这项能力形式化为 **workflow orchestration**，并给出 **145 个长程任务 / 8 个专业域 / 17 种任务形态**，每个任务给出初始工作区与**互为依赖的集成交付物**，由**隐藏 verifier** 判定。★ 实测口径（论文 Table 1/2 + 项目页 + 仓库 README 三方对照）：**最强配置 Claude Opus 5.5 + Claude Code + max effort 的 Overall Resolved 仅 36.95%**（八域等权平均），**最高 Overall Score 80.21**（Opus/high，SWE 96.98、MATH 97.44，而最高 SWE resolved 只有 29.41%）；**没有任何一个配置在所有域上都最好**；域间分化极强——Opus 在 **LAW 域 resolved 为 0.00%**，MATH 却有 95.83%；执行轨迹显示**两种委派风格**：高 effort 下 Claude 系（Opus/Sonnet + Claude Code）**发起 workflow 更少但每次 worker 群更大**，GPT 系（Astra/Sol + Codex）**发起更频繁但每次 worker 更少**；**workflow 迁移实验（32 个难任务，源模型只写 workflow、不得改工作区）**：Opus 写的静态 workflow 让四个执行模型**平均提升 +6.41 分**（Kimi K3.1 Pro 35.75→46.61、GPT-6 Luna 25.08→30.37、Doubao-Seed 20.39→28.04、DeepSeek V4.1 Flash 18.37→25.24）——**「强任务能力 ≠ 强 workflow
