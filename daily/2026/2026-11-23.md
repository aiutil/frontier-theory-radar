## 2. 先说结论
- **今天最值得看什么：** [Held While Waiting: What LLM Agent Sessions Reserve on Serverless and Agent Runtimes](http://arxiv.org/abs/2611.26480v1)（Mekhala Hithyshini Sreenivasa，AWS 雇员，论文声明独立完成、使用自有账户、未使用任何非公开 Amazon 信息）。
- **为什么值得看：** 它把「agent 运行时到底占了什么」从平台文档里的功能描述，变成了可测量、可复算的容量事实——而且答案直接命中我们自己的平台瓶颈（等待不计 CPU，但会话独占环境是照占的）。
- **最硬的四个结论（均已在论文正文逐条核对，且部分可用仓库 shipped 数据独立重算）：**
  1. **等待占比压倒性。** 部署态 agent step 只有 0.2%–1.5% 的时间在计算，模型回复等待中位数 2.7 s，计算仅 5–40 ms。
  2. **占用与利用率脱钩。** 任意时刻 1000 个被占环境里只有 2–15 个在用处理器，即每 1 核真实工作量占住 70–600 个环境；实测并发上限做到 400 个会话（results/capacity_validation.json 载有 50/100/200/400 四档实测核数）。
  3. **滞留是独立的一笔账。** 客服基准里会话平均只持续 33 s，但环境在客户端不显式关闭时会被多留 15 分钟——AgentCore 默认 5000 活跃会话配额（多数区域 2500）先于算力被撞到。
  4. **共享的账可以重算。** 本轮用 shipped 的 results/remedy_sim.json 重算：k=64 时 envs_mean 从 1007.57 降到 16.81（比值 59.93），同配置 added_latency_ms.p99 = 39.67 ms；k=256 时环境比升到 209.40 但 p99 延迟升到 79.2 ms，说明共享有拐点。
- **工程可验证性：** 极好。github.com/MEKHALA/agent-runtime-capacity 实测可达（Apache-2.0，4864 KB），含 agentprof/（纯标准库 tracer + LangGraph/Strands 适配器）、scripts/measure_framework_cpu.py、scripts/simulate_remedy.py、scripts/validate_capacity.py、data/deployed_turns.csv（实测 3549 条数据行，与论文 3,549 steps 一致）、results/（含九平台调查表 PLATFORMS.md）、tests/test_agentprof.py、paper/figures/。README 给出复现时间表：本地表 2/图 1 约 15 min，Section 4.4–7 分析脚本秒级，且**全程离线、不调用任何模型、不烧 token**。

## 4. 今日深挖论文

- **一句话本质：** 它把「我的 agent 服务跑得挺稳」这句话拆开，问了一句之前没人系统问过的话——**你的服务在「不干活」的时候占着多少资源？** 而答案的形状很反直觉：agent 有 99.9% 的时间不计算，但平台照样为每个会话留着一个完整环境；于是 1,000 个会话只跑出 2–15 核的工作量，每核工作量对应 70–600 个被占环境。
- **底层问题：** agent step 的时间构成，以及这个构成如何决定平台的容量口径。按会话独占环境的运行时（AgentCore 每会话一个 microVM、Azure Foundry 每会话一个 sandbox、Vertex AI Agent Engine 同类），瓶颈不是算力而是环境配额——而「会话结束」在很多运行时里不是一个自动事件，需要客户端显式关闭才有 15 分钟滞留。
- **新命题 / 新方法 / 新证据：**
  - **命题（可复算）**：等待占比与计算占比之比，直接给出「每核工作量占用多少环境」这个容量系数。实测 0.2%–1.5% 在计算 → 1000 个环境里 2–15 个在用 → 每核 70–600 个环境。
  - **方法（测量的诚实性）**：模型在 socket 处被替换，框架 CPU 单独测；部署态观测用已发布的 3,549 个 warm step；延迟用 50 次模型调用 + 30 次工具调用标定。作者在 CALIBRATION-NOTES.md 里主动记录「the model-object stub that gave a wrong answer」——即第一次桩件测量是错的。
  - **证据（两条独立路径互验）**：解析式容量分析 + 实测最多 400 个并发会话的直接测量；以及离散事件仿真下 k=64 的 59.93 倍环境比与 39.67 ms p99 延迟（本轮用 shipped JSON 重算得出，与论文一致）。
  - **归因（两个可分开的成因）**：会话结束后环境滞留（33 s 会话 vs 多留 15 分钟，客户端可自行修复）；一个环境只服务一个会话而该会话 99% 在等待（需平台支持，所调查 agent runtime 中仅一个部分允许）。
- **研究位置：** 平台容量刻画 + 测量方法论 + 上线复盘，不是新 agent 框架。它与同批的 2611.26341（RoC，事件触发省 token −65.3%）、2611.26438（R2-VLA，Act/Ask 带风险保证）分处不同层次：单次调用 → 单次决策 → 跨会话容量。只做前两件，账单会降但配额墙还在。
- **工程可验证性：** 有明确代码入口，且几乎零成本可跑——Apache-2.0、纯标准库 tracer、本地基准约 15 min、分析脚本秒级、全程不烧 token；含九平台调查表 PLATFORMS.md（逐条带 [V]/[R]/[U] 核验标记）与可复现的图表脚本。
- **趋势关联：** 值得纳入趋势雷达继续观察。理由是它给出了一个会被别人复制的提问方式：**等待时占着什么**。可预期的后续是「合成负载 vs 真实 agent 负载的形状差多少」，以及把「会话滞留时间」当成平台 SLA 的独立指标。
- **长尾价值：** 三件可留存的资产：①「等待占配额」会进入 agent 平台选型的标准问法；②九平台四列对齐的可比性规格表（平台行为会变而口径不会变）；③「会话结束需客户端触发」这类隐式依赖客户端行为的坑，写进检查清单。
- **启发：** 先做价值路由，再决定深挖深度——今天 15 篇里只有这一篇值得逐句读；其余按 trend / long_tail / ignore 分流即可。工程上则是：任何「按会话数估容量」的做法，先问占用口径是什么；任何「拿现成负载压自己系统」的做法，先问负载保真吗（这与前几天记录的 2611.25905 的 trace replay 保真度问题同源）。

## 7. 启发

### 系统设计启发
- **「不干活时占多少资源」应该是容量模型的第一性比值，而不是事后补丁。** 2611.26480 的整条推导只用了两个数：等多久（2.7 s 中位）与算多久（5–40 ms），就得到 70–600 环境每核的容量系数。设计任何按会话/按连接隔离的系统时，这个比值值得先算一遍。
- **「会话结束」未必是一个事件。** 客服基准里 33 s 的会话把环境多留 15 分钟——任何按会话计数的配额，实际被客户端的连接管理质量决定。这类隐式依赖应该写进设计文档，而不是等踩坑。

### Agent 工程启发
- **等待与计算要分开记账。** agent step 只有 0.2%–1.5% 在计算，这个比例意味着优化「计算效率」的收益上限被结构性压低；真正该优化的是等待的结构——共享（k=64 时 59.93 倍环境数下降、p99 延迟 39.67 ms）比抢那几毫秒的 CPU 有用得多。
- **共享存在拐点，不要无脑加。** 本轮重算 shipped 仿真：k=256 时环境比升到 209.40 但 p99 延迟升到 79.2 ms（另一组参数下 1871 ms）。共享度是个需要实测选定的参数，不是越大越好。

### 研发流程启发
- **把「假装的模型」当作标准测法。** 论文在 socket 处替换模型来单独测框架开销，并明写第一次的桩件给出了错误答案（CALIBRATION-NOTES.md）。任何需要区分「我们的开销 vs 上游开销」的测量都该用这个套路，并把踩过的坑写进仓库。
- **证据分级要写进产物本身。** 九平台调查表 PLATFORMS.md 给每条结论打 [V]/[R]/[U]，作者还在文件末尾写「Before submission: re-fetch every [R] source」。这种自我标注让读者知道自己能信哪一部分。

### 评测方法启发
- **两条独立路径互验同一个结论，比一条路径做两次更可信。** 解析式容量分析 + 实测 400 并发会话，两个数字对上才算数。
- **均值与尾部必须分开报。** 本文的关键量（占用系数、p99 延迟）全是尾部分布；用均值描述「等待 vs 计算」会得到接近 1 的误导性结论。

### 平台工程启发
- **能力已经存在，只是没出现在 agent runtime 上。** 所调查的九个平台里，默认共享环境的全是通用运行时（Lambda Web Functions、Cloud Run、Cloudflare Workers），按会话独占环境的全是 agent runtime（AWS、Microsoft）。所以这是品类设计问题，不是能力缺失问题。
- **等待不计费 ≠ 等待不占配额。** 这两句话在成本核算里等价，在容量核算里完全不同。任何容量表都应该分列这两项。

### 个人学习启发
- **优先读那种「重新定义计量单位」的论文。** 这篇的价值不在新方法，而在把「agent 占了什么」变成了一个单位：环境。单位一旦确立，后面所有平台比较都有了共同语言。
- **今天 15 篇里只有 1 篇值得逐句读，其余分流即可。** 先做价值路由再决定深挖深度，本身就是这套方法论的演示。

## 10. 最终结论
- **结论：** 重点学习
- **价值类型：** 即时价值
- **原因：** 今天唯一一篇把「agent 运行时到底占了什么」量化到可复跑程度的论文，而且结论直接命中我们自己的平台瓶颈。核心问题：agent step 的绝大部分时间不是在算，而是在等模型；但按会话隔离的运行时（Bedrock AgentCore 每会话一个 microVM、Azure Foundry 每会话一个 sandbox）在等待期间仍然占着环境配额。论文正文逐条核对一致的数字：模型等待中位数 2.7 s、计算仅 5–40 ms（部署态实测「只有 0.2%–1.5% 的时间在计算」），于是任意时刻 1000 个被占环境中只有 2–15 个真正在用处理器——即每 1 核真实工作量要占住 70–600 个环境；实测并发上限做到 400 个会话；客服基准里一次会话平均只持续 33 s，但环境在客户端不显式关闭的情况下会被多留 15 分钟。九条解法中最有用的一条：我们实测 shipped 的 results/remedy_sim.json，k=64（64 个会话共享一个环境）时 envs_mean 从 1007.57 降到 16.81、比值 59.93，且该配置 added_latency_ms.p99 = 39.67 ms——即「59 倍更少的环境」与「99/100 的回复延迟不超过 40 ms」这两个数字可以从仓库数据独立重算出来，不是作者单方面主张。工程可验证性极好：github.com/MEKHALA/agent-runtime-capacity 实测可达（Apache-2.0，4864 KB），含 agentprof/（纯标准库的 span tracer 与 LangGraph/Strands 适配器）、scripts/measure_framework_cpu.py、scripts/simulate_remedy.py、scripts/validate_capacity.py、data/deployed_turns.csv、results/、tests/test_agentprof.py 与 paper/figures/；README 明确给出「表 2/图 1 本地复现 ~15 min、Section 4.4–7 分析脚本秒级复现」，且全程离线、不调用任何模型、不烧 token。对我们的直接产出：我们自己的 agent 服务要区分「计费口径」和「配额口径」——等待不计 CPU 不代表不占环境，而 AgentCore 默认 5000 活跃会话配额正是先撞到的墙。
- **最大不确定性：** 1. **九平台调查表的口径本轮未逐条复核。** 论文的 results/PLATFORMS.md 给每条打了核验标记，但多数条目标为 [R]（取自研究 agent 报告、未独立复核），作者自己在文件末尾写「Before submission」一节要求 re-fetch every [R] source。本轮只实测了 GitHub/arXiv 侧，未重新抓取这九个平台的当前文档，因此「哪些平台共享环境、哪些按会话独占」这一结论应按作者自述处理。其中 [V] 标记的条目（AgentCore 定价页的「CPU scales to zero during I/O wait」、Lambda Web Functions 扩容文档、AgentCore 的 idle 120 秒回收与 5000/2500 会话配额）证据相对更硬。

2. **5–40 ms 的计算时长是推算值，不是直接测量。** 论文自述「The milliseconds are an estimate because they are hard to measure — a stubbed model, a timer around the model call, and steps run back to back each gave a plausible number that was too low」。因此「等待 vs 计算」的具体比值带系统性不确定性；可信度更高的量是「0.2%–1.5% 在计算」这一部署态比例（来自 3,549 个真实 step）与由此推出的 70–600 环境系数（该系数同时被 400 并发直接测量交叉验证）。

3. **CPU 计量口径按框架不同，不能混用。** 论文 threats 节明确：LangGraph 的 CPU 是按线程计（其工具节点用线程池，需显式追踪），Strands 是跨两个线程的过程级 hook 窗口（其模型调用跨线程），两种时钟不可混算；并指出背靠背循环的基准会把 CPU 开销低估（真实「等完再算」对 LangGraph 约 2 倍、对 Strands 2–5 倍）。因此表中常数不可跨框架直接套用。

4. **仓库社区验证为零。** github.com/MEKHALA/agent-runtime-capacity 实测 0 star / 0 fork，created 2026-10-31、pushed 2026-11-16。上游依赖（LangGraph 0.6.11、langchain-aws 0.2.35、Strands 1.55.0、boto3 1.42.97）已在 cloud/requirements.txt 固定，但项目本身无第三方使用痕迹。

5. **部署数据的 harness 不在工件内。** README 明确 data/deployed_turns.csv 收集自 2026 年 9 月的独立研究，模型时间是在模型客户端调用周围测的（因此含客户端自身的序列化开销），且「The deployed study's own harness is not part of this artifact」。论文第 3.3 节说明部署 CPU 每 step 是被**夹逼**（bracketed）而非直接测得的。

6. **仿真里的内存数字是示意性的。** README 明确「The simulation's memory figures rest on an illustrative footprint (0.5 GB per process plus 10 MB per session); its environment counts do not.」——即环境数结论可信，内存结论不应当作实测。

7. **环境限制导致的未核验项。** huggingface.co 在本环境持续连接失败（多次 curl 超时），因此论文涉及的部分 HF 权重入口与同批其他论文的 HF 数据集（2611.26613 的 AgentRoboCritic-Bench / -Dataset / Muse-Glimmer-30B，2611.26557 的 ALIENS232/MM-SystemOneBias，2611.26438 的 miniVLA 权重）本轮无法独立下载验证，相关规模只按作者自述处理。
