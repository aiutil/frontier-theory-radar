## 4. 今日深挖论文

- **一句话本质：** 生成式引擎把「一批问题」当成「一串 token」，于是多问题场景要么重复算前缀、要么插入分隔符污染输入；Flide 说这件事应该反过来——**逻辑上是一棵树，物理上是一条流，树形写进 GPU 常驻元数据，让每个分支各自看到与「单独问它」完全相同的输入**。
- **底层问题：** 决策模型（Jev / OneJev / Open-Jev 等 System One 模型）的推理形态与传统 LLM 不同：**它不生成 token，直接输出每个选项的分数**。但现有推理引擎全是为「生成」设计的，于是把决策请求硬塞进生成式管线时出现两类损耗：一是**前缀重算**（同一条 state 下的多个问题各跑一遍共享前缀），二是**输入被污染**（多选项打分时插入的分隔符会进入每个分支的输入，**改变概率、翻转决策**）。后者更危险——它不是慢一点，是**答案不一样了**。
- **挑战了什么旧假设：** 挑战的是「**多问题共享前缀就等于多问题看到同一个前缀**」这个假设。在标准 attention 里用 mask 就能让分支互不可见；但 **Gated DeltaNet 这类递归层会把之前的每一个 token 折叠进一个递归状态**，分支会从兄弟分支继承状态。于是「物理上并排、逻辑上隔离」在递归层上做不到——除非每个分支能在**同一趟**里从主干的确切状态重启。
- **新假设：** 「**每个问题的答案，应当等于它单独被问时的答案**」——这不是性能优化目标，而是**正确性契约**。论文把它写成 *exact arithmetic* 下的保证：ForkAttention 跨普通 attention 与 Gated DeltaNet 层用 GPU 常驻索引导航请求依赖，使得每个 query 分支的求值与孤立前向完全一致。这条契约的价值在于它**可以被机器检查**，而不是靠信任。
- **核心机制：** 三件事。(1) **逻辑/物理解耦**：一轮请求排成一条扁平 token 流，分支拓扑记录在 GPU 常驻元数据里，用一组预录制的执行图容纳多样的请求组合。(2) **ForkAttention**：attention 与 Gated DeltaNet 层都按这份元数据导航，在同一趟里让每个分支从主干的确切状态重启。(3) **可选的 batch-invariant 模式**：固定浮点归约顺序，**让同一个请求无论怎么分批都得到相同的比特**。论文 Table 1 的对比结论是：Flide 是唯一一个同时做到「单趟执行 / 输入不被污染 / 混合模型任意分叉 / CUDA graph 可重放 / 可选模式下逐比特不变」的引擎。
- **新能力：** 之前做不到的事，现在有了确定的做法——**把「同一个 state 下的多个问题」当成一次原子操作来打分，而不必担心批处理改变结果**。这直接解锁了两件工程上一直很别扭的事：一是决策模型的**高并发重排/路由**（一次 forward 打分 k 个候选，而不是逐条问）；二是**可复现的评测**——批大小不再是隐变量。
- **限制条件（今日逐条核对，边界写清楚）：**
  - **加速比不是普适的。** 论文摘要写「up to 9.5× faster than vLLM and SGLang」，**官方仓库 README 写的是「up to 9.4×」**，两者口径不一致；论文正文比摘要保守得多——单问题场景「cuts the latency of a lone request by up to **3.2×**」，且明确写「**Under load, where model computation dominates, Flide matches the best baseline**」。9.5× 成立的前提是「**一个 state 带多个问题**」（正文：up to 9.5× lower latency、8.5× higher throughput）。**对单请求场景要按 3.2× 甚至「打平」来预期。**
  - **精确性主张本机无法复算。** 今日实测 `flide verify --device cpu` 已把 Qwen3.5-0.8B 完整拉起（`read 1.71 GB of weights in 50.6s`），**但在第一层 RMSNorm 处失败**：`RuntimeError: 0 active drivers ([]). There should not be one`。根因在代码层——`flide/kernels/pointwise.py` 直接 `import triton` 并用 `@triton.jit` 写死 rms_norm / swiglu，`flide/verify.py` 硬编码 `backbone_options={"cuda_graphs": True}`，**无 CPU 回退**。→ **要验证必须上 GPU（H200 级）。**
  - **实测精度侧数据（论文 Table 4 / README）：** Flide 的 top answer 在**每个 workload 上**都最接近 float32 参考（四个尺寸平均），且「accuracy stays within **1.2 points** of vLLM's in every cell」；批大小改变答案的比例 Flide ≤ 0.2%、SGLang ≤ 1.7%、vLLM ≤ 3.2%。

- **研究位置：** 这不是源头论文，是**把已有的一类模型（Jev / 决策模型）接入已有基础设施（vLLM / SGLang）时补上的一块**。它上承 2026-10-28 本仓库已跟踪的 DecisionRAG（同为决策模型路线）与 2026-10-17 的 RealtimeBench（同为 Jev 对照 GPT-6.1-sol 的时延实验）；下游接的是 DecisionRank（今日另一篇，把决策模型用到重排上）。**三篇串起来是一条清晰的线：决策模型从「论文原型」到「有专用引擎」到「有工业界任务落地」。**

## 7. 启发

### 系统设计启发
- **「逻辑结构 vs 物理执行」应当是所有请求编排系统的第一分层。** Flide 的核心不是快，而是先把「这批请求在逻辑上是什么形状」与「GPU 上实际怎么跑」拆开。**我们自己的 agent 编排层同样存在这个混淆**：一次决策要并行探查 5 个工具返回，我们通常把它写成「5 次并发调用」，于是前缀被重算 5 次、上下文被拼接 5 次。**先问「这 5 个探测共享什么前缀」——这是可以抽出来单独设计的。**
- **「批大小会改变答案」应当被当作默认会发生的事。** 论文实测：Flide 在 1–64 clients 间最多改 0.2% 的答案，vLLM 最多 3.2%、SGLang 最多 1.7%。**批处理顺序和批大小在浮点归约下是有语义后果的。** 我们自己的批量评测脚本如果把同一 passage 的多个问题拆到不同 batch，**分数是被悄悄改掉的，而我们会把它当成方法差异**。→ **一条立即可做的检查项**：凡是同一输入被拆批打分的评测，重跑一次不同 batch size，看结论动不动。
- **把「性能数字」和「正确性契约」分开验收。** Flide 同时给出 9.5× 和「每个分支等于它单独跑一次」——后者是**可以被机器验证的契约**（它甚至提供了 `flide verify` 与 `--batch-invariant` 模式）。**我们的很多优化只承诺前者。** 能给出「在什么条件下输出必须完全一致」这种可断言契约的优化，可信度远高于只有一个平均加速比的优化。

### Agent 工程启发
- **决策模型的路由成本正在塌陷，这是可以现在就用的一层。** 今日实测：vLLM 与 SGLang 主干均已合入 `/v1/systemone`；Flide 官方 README 列出 16 个模型族；`flide formats` 实测同样列出这 16 个；社区侧也有独立实现（anessbelbati/jev-rerank-bench、hgqimo/JevRanker）。→ **「哪些请求根本不需要 LLM 生成」正在变成一个纯工程问题**，而不是模型能力问题。我们的路由层（哪些请求走生成、哪些走分类/打分）**今天可以重新标定一次**。
- **「分工是被搜出来的，不是被设计出来的」——这是 RoboArchitect 今天给出的最贵的一条洞察。** 它的 README 写明：不给任何分工指令，演化出的 agent 大多**收敛到 VLA policy 与 code-as-policy 之间的动态切分**（模型做它擅长的，代码接管它失败的地方，修好了再交还）。→ **对我们的 agent 架构：当底座模型与任务不匹配时，「哪些事交给模型、哪些事交给代码」可能不该由我们拍板，而应该由一个评测闭环搜出来。**
- **失败修复的关键不是「重跑」，而是「先判定哪些中间产物仍然有效」。** Dittany 的贡献图 + 双作用域修复（输入足够时做 action-level correction，前提不对时做 graph-level recovery，且**保留已验证的贡献**并在下游使用前复检）是一条可以直接抄的机制。→ **我们自己的 agent 失败处理，第一步应该是「标注哪些步骤的产物仍然可信」，而不是「从头再跑一遍」。**

### 研发流程启发
- **抓取口径本身需要被当成一条会被审查的代码路径。** 今日实测：arXiv 同一天（published 2026-10-30）在 12 个分类下**有 200+ 篇**，而 `fetch_papers.py` 的 `max_results_per_category=10` **只留下 10 篇**；今日逐条核对被丢掉的内容，**里面有一篇与入选论文直接竞品（ZHA vs LSA）、一篇与入选论文同组作者的姊妹篇（PLD FFT vs Counting on Dummies）**。→ **不是所有截断都是良性的。** 流水线需要一条「**同批次覆盖度自检**」：定期用更宽的查询复查当日批次，报告真实规模与被丢弃的数量。**今天的结论是：雷达当前存在已知的系统性选择偏差。**
- **「论文承诺了代码」与「代码已经可用」之间要分三档记录。** 今日三个典型：LARC 仓库真实存在但**只有 README**，TODO 三项全未勾选、作者承诺 11/9 放推理代码；critic-matters 论文 comment 写「Project page and code」，但项目页**没有任何 github 链接**（页面里唯一的仓库是 FLUX 本体，不是本文代码）；RoboArchitect 仓库**完整但无 license**、stars=0。→ **今天起，「有仓库链接」这一档不足以作为工程可用性的证据，要按「能装 / 能跑 / 有测试」分别记。**
- **复现一条论文主张之前，先看它的实现依赖了什么执行后端。** 今日 Flide 的失败给了一个极高效的判据：**读一眼 kernel 是不是 Triton/CUDA 写死的**。这一步 5 分钟就能把「今天能不能验」从「试一下看看」变成确定答案，从而把有限的验证时间投给真正可验的论文。

### 评测方法启发
- **「用算法自己的运行数据算出理论松弛的缺陷」是一种可借用的评测范式。** 今日 2610.42133 提供的观察是：除渐近步之外，**所有缺陷项都能从算法自己的运行里算出来**。→ **可迁移成一条自检问题：我们每个评测结论背后的不确定性，能不能被算出来？** 如果只能靠「我们相信它稳定」，那它就该被降级。
- **主观评测的口径必须写进结论。** Dittany 的「84.76%」背后是 8,758 个 resolved label，并**排除了 164 个 ambiguous run 与 78 个 format-only discrepancy**，语义评估由 DeepSeek V4 Flash 判官完成、未做人工双评。→ **引用别人的主观分数时，要把它的判官与排除规则一起搬过来**，否则等于引用了一个没有单位的数字。

### 平台工程启发
- **超长上下文的成本问题，今日同时出现了两条互补路线。** LSA 走「层次化聚类 + 稀疏读取」并**已做成 SGLang fork 分支与 Docker 镜像**；ZHA 走「层次化树结构 indexer」并声称 asymptotically subquadratic——**而 ZHA 被今日的抓取上限丢掉了**。→ **平台侧选型时，这两条必须成对评估**；同时注意 LSA 的 22.7×/72.4× 是「**单层 attention 层**」的数字，不是端到端数字（端到端待核验）。
- **DP 训练栈里「批大小可被观测」是一个真实的工程缺口。** 今日三篇相关论文串起来看：Counting on Dummies 用随机 dummy points 掩蔽批大小并让截断仍保有隐私保证（作者均来自 Apple），其依赖的 PLD 会计器正是同组作者的 2610.42117（**也被今日抓取丢掉了**），而仓库 moshenfeld/PLD_accounting 与 PyPI `PLD-accounting`（今日实测版本 2.0）今天真实可用。→ **我们若自建 DP-SGD 流水线，批大小泄露与截断这两件事应进威胁模型；但要先确认会计器用哪一版。**

### 个人学习启发
- **今天最值得记的不是某篇论文，而是一条判断法：「看它有没有变成别人仓库里的一个目录」。** Flide 的价值判断之所以有今天这么硬，靠的是 vLLM/SGLang 主干里的那两个目录，而不是它自己的 benchmark 表。
- **同时也要记住反面：目录存在不等于结论成立。** Flide 的精确性今天仍未被我们验证——**「生态已接受」和「数字已复核」是两条独立的证据线，不可互相替代。**
